# 整桩日志 AI 辅助分析 —— 组内同步说明

## 1. 这件事是什么

目标不是做一个“把日志丢给大模型、随便出结论”的聊天工具，而是做一个：

**给研发和售后用的、有证据支撑的整桩日志诊断平台。**

用户上传日志后，系统能告诉你：

- 大概出了什么问题
- 依据是哪些日志和哪几行证据
- 哪些结论已经比较确定
- 哪些只是可能原因
- 还缺什么证据，建议怎么继续查

---

## 2. 目前已经完成了什么

目前还是**个人本地工具**，不是正式产品，但基础已经搭起来了。

### 已经有的能力

- 能分析整桩日志，不只看 CCU，也覆盖网络、OCPP、充电过程、功率、电表、系统等
- 已经沉淀了 **19 个正式案例**，每个案例都有：
  - 日志范围
  - 人工结论
  - 期望结果
  - 禁止误报
- 已知案例回归结果：**19/19 通过**
- 已经开始做“盲测”：用不提前告诉答案的新日志，检验工具对未知问题的能力
- 已经整理了一部分协议、架构、错误码知识

### 目前还不够的地方

- 还是本地 CLI，只有少数人能用
- 还没有真正的多人协作平台
- 对**未知日志**的自动诊断还不强  
  - 首轮盲测里，已经有答案的 2 个案例，工具都没能准确命中根因
- 手头还有 **300+ 条人工分析过的日志**，但还没有统一整理成标准数据集

一句话：

> **现在有“能跑、有证据、能回归”的内核；还没有“多人可用、能持续学习、能上云”的产品。**

---

## 3. 核心判断

### 不要直接做的事

- 不要把 300 多条原始日志直接喂给大模型
- 不要一开始就追求“一个模型包打天下”
- 不要一边做盲测，一边针对单个案例临时改规则

### 应该做的事

1. 先把人工分析变成标准数据资产
2. 用规则保证证据和时间线可靠
3. 用大模型辅助解释、归纳、给排查建议
4. 最后再做成组内可用的私有云平台

推荐架构：

```text
日志上传
  → 自动解析 / 抽事件 / 排时间线
  → 规则引擎给证据和候选结论
  → 大模型做解释和相似案例参考
  → 输出报告
  → 专家纠错
  → 回写数据集和评测
```

---

## 4. 300+ 案例怎么用

这些案例最有价值的不是“原文很多”，而是能变成统一格式的训练和评测材料。

每条建议至少包含：

- 日志包
- 机型 / 软件版本 / SN
- 故障时间窗
- 客户现象
- 人工根因
- 证据行
- 反证
- 还缺什么证据
- 建议动作

然后分成三类：

| 类型 | 作用 |
|------|------|
| 训练集 | 用来改进规则、知识库、大模型提示 |
| 验证集 | 用来调参数、看效果 |
| 盲测集 | 长期锁定，专门测泛化能力，答案不能提前暴露给模型 |

建议目标：

- 300+ 条先全部登记
- 至少 150 条做成高质量“黄金标签”
- 至少 50 条做成长期盲测集

---

## 5. 明年方向（建议）

前提已经明确：

- 原始日志优先放**公司内网 / 私有云**
- 明年先做 **10–30 人组内试点**，不急着做成大规模生产平台

### Q1：把数据理顺

- 整理 300+ 历史案例
- 统一标签格式
- 建立盲测集
- 把现有“一个案例一个规则”逐步改成通用能力

### Q2：提升未知问题诊断能力

- 自动找故障时间窗
- 自动判断问题大类
- 接入内网大模型 + 知识检索
- 用盲测看真实准确率

### Q3：做成组内可用的私有云试点

最少要有：

- 上传日志
- 后台自动分析
- 看报告和证据
- 专家纠错
- 权限和审计

### Q4：形成闭环

- 专家纠错能回流到数据集
- 每月做一次盲测复盘
- 再决定是否扩大到更多人使用

---

## 6. 明年验收建议看什么

不要只看“接没接大模型”，建议看这几项：

1. **盲测准确率**：对未知案例能不能判对领域和根因
2. **证据可靠性**：结论能不能对应到具体日志证据
3. **处理效率**：一个日志包大概多久出结果
4. **组内采用率**：试点同学是不是真的在用、愿意纠错反馈

---

## 7. 组内需要一起确认的事

1. 原始日志能不能进内网平台，脱敏要求是什么
2. 300+ 历史案例谁负责审核、谁有权限使用
3. 私有云资源是否已有：对象存储、数据库、任务队列、SSO、GPU
4. 第一年优先解决哪几类问题，不要什么都一起做
5. 谁来当这块的长期 Owner，以及需要多少开发支持

---

## 8. 最近四周建议先做的事

1. 先盘点 300+ 案例：机型、问题类型、能不能脱敏、标签完不完整
2. 定一套统一案例格式，先用 20 条试标
3. 补齐当前盲测答案，冻结第一版泛化基线
4. 确认私有云基础资源
5. 做一个最小闭环演示：

```text
上传 ZIP → 自动分析 → 出报告 → 专家反馈入库
```

---

## 9. 一句话总结

> 我们现在有一个本地可验证的日志诊断内核，和一批很有价值的人工案例。  
> 下一步不是急着堆模型，而是先把案例标准化，再做成内网多人可用的诊断平台。  
> 大模型负责解释和辅助，规则和证据负责把关；最终目标是让更多人一起用、一起纠错、一起把能力滚起来。
